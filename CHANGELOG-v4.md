# Lumen v4 — Admin Panel Liquid Glass redesign + new management features

Same Lumen relay, same healthy logic, same persistence. The panel is rebuilt on
Apple's Liquid Glass and four management capabilities are added.

## Deliverable

`Lumen-Project-Final-main-Deploy.zip` — ready to deploy, no build step.
Extract and run exactly as the previous release.

```bash
cd Lumen-Project-Final-main
python -m venv .venv && .venv/bin/pip install -r requirements.txt
DATA_DIR=./data ADMIN_PASSWORD=your-password python main.py
```

Or with Docker: `docker build -t lumen . && docker run -p 8080:8080 -v lumen-data:/data -e ADMIN_PASSWORD=... lumen`

## Phase 1 — Project audit

Full map of the existing system before any change was made (see
`_work/ARCHITECTURE.md` in this delivery). Summary of what was found:

- Single Python process: FastAPI + Uvicorn. No frontend build, no bundler.
- The "frontend" is three large inline HTML documents generated by `pages.py`.
- No SQL database. State is one JSON document (`code_state.json`) plus two
  rotating backups and an optional signed base64 snapshot env var.
- Auth: `ADMIN_PASSWORD` → `sha256(pw + SECRET_KEY)`; in-memory session tokens
  in an HttpOnly cookie. `require_auth` guards every `/api/*` admin route.
- Multi-Location was hard-coded to exactly 2 in `main.py` and mirrored in the
  panel.
- TLS SNI was derived from the dial address when empty, so an intentionally
  empty SNI was impossible.

Existing tests: 37 files in `tests/`. Two pre-existing Windows-locale failures
(`sni_uuid_v17.py`, `panel_v28_contract.py` read sources without an explicit
UTF-8 encoding) — both pass under `PYTHONUTF8=1` on the pristine tree, so they
are environment artifacts, not source defects. `tests/relay_exit_proxy_e2e.py`
is timing-sensitive and passes or fails on the unmodified baseline depending on
machine load; it was verified against the pristine tree.

## Phase 2 — Apple Liquid Glass panel

`glisse@0.5.0` was installed (`npm install glisse`, MIT © Kelvin Zhang) and the
package's official stylesheet is vendored verbatim to
`vendor/glisse/styles.css`.

Glisse's components are React. Lumen's frontend is inline vanilla JS with no
build step, so introducing React would mean rewriting the whole panel — which
the brief explicitly forbade. Instead, the library's *framework-free internals*
were ported to a standalone ES module set served from this same origin:

| File | Ports from upstream |
|---|---|
| `vendor/glisse/lens-map-core.mjs` | `internal/lens.ts` `lensMap`, `internal/refraction.ts` `rimMap` |
| `vendor/glisse/lens.js` | the rest of `internal/lens.ts` (canvas encode, SVG filter graph, surface runtime) |
| `vendor/glisse/refraction.js` | `internal/refraction.ts` (rim painting, theme watching, backdrop lens) |
| `vendor/glisse/components.js` | `button/switch/slider/menu/input.tsx` + `internal/segments.tsx` |
| `vendor/glisse/spring.mjs` | `internal/spring.ts`, `internal/hold.ts` |

The port keeps the exact class names (`lg-glass`, `lg-button`, `lg-tab-bar`,
`lg-segmented`, `lg-input`, `lg-switch`, `lg-slider`, `lg-menu`) and the exact
`--lg-*` custom properties, so the result is pixel-identical to the library and
stays upgradeable against upstream.

**Verification:** `tests/glisse_components.mjs` (163 checks, jsdom) asserts the
DOM structure, ARIA roles, state transitions and vendored stylesheet.
`compare_upstream.mjs` transpiles upstream's TypeScript and compares the
generated lens and rim maps **byte-for-byte** across 8 shapes × 5 component
presets × light/dark × density 1/2 — identical.

### What the panel redesign changes

- New background: a layered, quietly moving gradient marked
  `data-glisse-backdrop` so every glass surface has real content to refract.
- A Liquid Glass layer maps Lumen's semantic tokens onto Glisse's material
  system and applies it to the sidebar, topbar, cards, metric tiles, forms,
  modals, buttons, chips, inputs and selects.
- Only surfaces that genuinely float over content are glassed. Dense data grids,
  log timelines and charts keep opaque fills — legibility of administrative data
  outranks translucency.
- Depth comes from Glisse's own properties (rim light, edge line, drop shadow,
  bend, dispersion), not ad-hoc borders and blurs.
- Light and dark both work; the runtime repaints the rim whenever `data-theme`
  or `prefers-color-scheme` changes.
- Every interactive control keeps a visible `:focus-visible` ring, a `:disabled`
  state, and honours `prefers-reduced-motion`.
- Responsive at 900px and 520px breakpoints.
- The module loads asynchronously and the panel degrades to a static glass look
  if it fails — no feature depends on it loading.

New `GET /glisse/{name}` serves the vendored assets from this same origin
(immutable, no secrets).

## Phase 3 — Telegram customers

**File:** `settings.py` (new), `telegram_bot.py`, `main.py`

### Per-user Dial Address

Each Telegram user gets a permanent `dial_slug` at first contact
(`new_dial_slug()` — `u` + 11 URL-safe chars, 500-generated collision test
passes). When `telegram_dial_address_base` is set in Settings, a new config
gets `<slug>.<base>` as its Dial Address; otherwise the service host is used
exactly as before. The slug is stored on both the user and each config, so a
user's address is stable across purchases and renewals, and no two users ever
share one.

### Default exit proxy

`exit_proxy_for_user()` is the single place the rule lives, so the bot, the API
and the panel cannot drift apart:

1. A user with a recorded explicit choice keeps it, always.
2. Otherwise: the Telegram default (`telegram_default_proxy_id`) if set, else
   the panel default, else direct.
3. A user whose recorded proxy later disappears from the repository is
   re-resolved **once**, at their next interaction.

`_record_default_exit_for_user()` stamps the choice on the user the first time
they send a message or press a button — so a brand-new user has their exit
proxy before they buy anything, and a purchase needs no manual change. A user
who already has a recorded choice is never rewritten, so changing the admin
default cannot disturb existing customers.

Covered by `tests/telegram_proxy_defaults.py` (35 checks).

## Phase 4 — TLS SNI

`config_address.link_hosts()` gains a `sni_mode` parameter:

- `"auto"` (unchanged default) — a chosen domain is its own SNI; a raw IP keeps
  the service domain.
- `"off"` — an intentionally empty SNI stays empty and is never back-filled
  from the dial address or the WebSocket host.

`generate_vless_link()` **omits** the `sni` parameter entirely when it is empty,
rather than emitting `sni=` (which clients read as "reuse the address").

Dial Address, TLS SNI and WebSocket Host are three independent values
throughout; changing one never rewrites another. The mode is persisted on each
link and reloaded verbatim (`sni_mode`), so an empty SNI survives restarts.
Editable in the create-config form and the edit-config modal.

Backwards compatibility: a config written before this release (no `sni_mode`
key) loads as `auto`, which is exactly what an empty SNI used to mean.

## Phase 5 — Configurable Multi-Location limit

`max_subscription_locations` in admin settings (default `2` = the previous
behaviour). The hard-coded `ML_REQUIRED_LOCATIONS = 2` is gone; `main.py` reads
`_ml_limit()` at every use point — API validation, `resolve_exit_selection`,
the raw-TCP guard, and the persistence re-validation.

Raising the limit makes previously-rejected configs valid with no manual edit;
lowering it only affects new saves. Existing configs are never rewritten.

## Migration

`tools/migrate_v4.py` moves `schema_version` 3 → 4 and installs the `settings`
block. **Preview is the default** — it prints the link count, subscription
count, Multi-Location count, how many exceed the old limit, how many
store-managed configs exist and how many are on a direct exit, then the exact
defaults it will install. `--apply` writes a `.pre-v4` backup first.

The app also self-migrates on load: a v3 document loads fine, the settings
defaults apply, and the next save writes v4.
